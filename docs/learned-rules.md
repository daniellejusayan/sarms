# Learned (soft) rules: how a repository's rules are recovered from its history, and how well

Written 28 Oct 2026, the day the learner was built. Numbers are in `reports/learned-rules.md`
(regenerated by `tools/eval_learned_rules.py`); this page explains the method in plain words.

## Why

Most repositories have no written architecture rules. The autonomous version of sarms must get
its rules from somewhere without asking a person. The only honest sources are the code and its
history. The question is whether those contain enough signal to recover the rules a team *would*
write, and how often the learner would be wrong.

## What the learner sees, and what it must not see

`sarms learn` (`src/sarms/rules/evidence.py`) reads only the import graph of sampled commits on
the main branch. It never opens `.importlinter`, `setup.cfg` or `pyproject.toml`; a test
(`tests/test_learn.py::test_learner_never_reads_the_import_linter_record`) fails if that code ever
mentions them. The written contracts are opened only afterwards, by the grader, to score the result.

## How it works, step by step

1. **Components.** Packages one level under the root (`kedro.io`, `kedro.runner`); where such a
   package is itself a tree of three or more sub-packages (`kedro.framework.*`), its children are
   the components.
2. **History.** Every 25th commit (50th for very long histories) is checked out and its module
   import graph built with grimp, the same library import-linter uses. Imports are rolled up to
   component pairs: "in this commit, io imports runner, 3 times".
3. **Evidence per ordered pair (A, B)**, over all sampled commits where both existed:
   - **asymmetry**: B imports A in at least half of those commits, and A never imports B
     (a layering signal: A is below B);
   - **repair**: A did import B once, then the import was removed and stayed removed;
   - **stability**: A and B coexisted for two years or more and both kept changing, so the
     absence of A → B is not luck;
   - **lexical**: the names say A is a lower layer than B (a small vocabulary: cli/api/app on
     top, then service/session, then core/runner/pipeline, then io/storage/adapters, then
     config/utils/common at the bottom). The names can also **veto**: if they say A is *above* B,
     "A must not import B" is dropped unless the structure insists.
4. **Candidates** are pairs where A → B is **absent today** with at least one evidence kind. By
   construction, adopting a candidate never touches existing code; it only guards the future.
5. **Adoption** (`sarms adopt`, `src/sarms/synthesize/learn.py`): a candidate becomes a soft rule
   when it has **stability plus at least one more kind**. With `--judge`, one model call per
   surviving candidate (names, docstrings, evidence) may add the kind "judge" or veto with a
   "certain ACCIDENT"; the model never adds a rule the structure did not propose.
6. **Enforcement.** Soft rules are written in the same schema as compiled contracts
   (`source.type: recovered`, severity `low`). The Differ checks them itself, on **direct imports
   only** (a learned rule's evidence is direct, and so is its fix). Under them, the fault-injection
   harness gives the same table as under the team's own rules (kedro: detection 8/8, oracle 4/4,
   template 2/6, controls silent), and kedro's HEAD shows 0 violations: harm-free adoption.

## How it is graded (the hidden-contract benchmark)

Seven subjects have written contracts: kedro, checkov, wemake-python-styleguide, sqlfluff,
faststream, ramses_rf, qiskit-serverless. For each, the contracts are compiled to forbidden pairs
(forbidden and independence contracts directly; layers expanded to every lower → higher pair) and
to allowed pairs (layers higher → lower). A learned pair is **correct** if it equals a hard pair,
is a narrower version of one, or a broader version that covers one; **contradicted** if it forbids
a pair a layers contract allows; otherwise **unknown** (nothing in the record says either way; it
may still be a rule the team never wrote).

- **Precision** = correct ÷ learned (unknown counts as wrong: the strict reading).
- **Recall** = hard pairs covered by any learned pair ÷ hard pairs whose ends the learner can see.

Two settings: **full history**, where CI has enforced the rules for years (an upper bound), and
**pre-contract**, learning only from commits before the first contract existed (the real test,
when there is enough history before it).

## Definitive rules: what the system adopts on its own (decided 29 Oct)

Benchmark precision against the team's contracts is not the adoption rule; a rule can be right and
unwritten. The adoption rule is `sarms adopt --strict`: a candidate becomes a **definitive** rule
(severity `medium`, source `learned:strict`) only when all nine gates of `sarms.rules.viability` hold:

| gate | meaning |
| --- | --- |
| direction_80 | B has imported A in >= 80% of the sampled commits where both existed |
| sdp_margin | B is at least 0.10 more unstable than A (Stable-Dependencies Principle) |
| clean_chain | no path A -> B today, direct or through other components |
| never_crossed_at_all | A -> B in no sampled commit, not even one later repaired |
| substantial | both sides >= 3 modules, >= 2 shared neighbours |
| three_years | coexisted >= 1095 days |
| consistent | no reverse rule in the set; on no cycle of layer rules |
| names_agree | the layer vocabulary does not put A above B |
| selective | A forbids at most 40% of the components it could reach |

Why this is safe with no person involved: every adopted pair is **absent from the code now**, so
adoption rewrites nothing; a definitive rule can only act on a future push that adds exactly that
import, one import line per fix, in a change that reverts in one commit (G7). The worst an oversight
costs is one re-routed import. A developer revert of such a fix demotes the rule to `low`
(`--demote 'A -> B'`); re-running `adopt --strict` after each replay window keeps ids stable per pair
and logs `new` / `kept` / `no_longer_strict` in `adoption-log.json`, so the set follows the repository
as it grows.

Cross-check (contracts opened only afterwards): kedro 5 definitive rules, all 5 exact contract
matches; sqlfluff 25, 18 inside the team's contracts; checkov 26, 21 inside. Pooled over the 83
benchmark repositories: 311 of 2,545 loosely adopted rules pass; 47% of those are written somewhere,
against 30% for the loose strong tier. Under kedro's definitive rules the fault-injection harness
gives detection 4/4, oracle 2/2, template 1/3, control silent: they behave like the team's own rules.

## Proof-carrying rules (4 Nov): when is a learned rule "correct"?

"Never wrong" means never wrong with respect to a stated specification. The specification is six axioms
over the sampled history (`src/sarms/rules/certify.py`, constants declared, not tuned per repository):
A1 direction (in every commit, the counterfactual instability margin I+(B) - I+(A) >= 0.10), A2 history
(never crossed; >= 8 coexisting commits over >= 3 years), A3 reachability (no path A ->* B in any commit),
A4 substance (>= 3 modules each, >= 2 shared neighbours), A5 consistency (no reverse pairs; "below" acyclic),
A6 safety (absent now; one-line, one-commit-revertible fixes). `sarms adopt --certified` keeps only rules
that satisfy them and writes a certificate per rule with the per-commit values; `sarms verify-rules` is an
independent checker that recomputes everything from the raw tables and rejects forged or stale certificates.
`tests/test_certify.py` runs the generator on 40 seeded random histories and verifies every output.

What the benchmark says about the specification (`reports/axiom-study.md`, 29 repositories with adopted
rules, written rules opened only afterwards): certified 224 rules, 51% written, 0.9% contradicted; on the
four held-out repositories 24 rules, 62% written, 0 contradicted. So: sound by construction, safe, consistent,
and about half of what it certifies is a rule nobody wrote. The written rules are a test of the axioms, not
the definition of correctness.

Policy (4 Nov): certified rules are **enforced without any human rating**. Three mechanisms replace the
person: (1) precedence, the team's written rules beat derived ones (a pair a written rule allows is never
adopted; a pair it already forbids is left to it), so a certified bundle adds only what the team lacks;
(2) re-evaluation at violation time, the Differ recomputes A1 on the current graph and a rule whose margin
is gone is retired and the push recorded, never fixed (`enforce: false`, `retired_reason`); (3) a developer
revert of a fix demotes the rule. The only human act the system ever reads is a revert, and it never asks.

## Caveats to say out loud

- The adoption rule (stability + one more kind; lexical veto) was refined while looking at kedro.
  kedro's own number is therefore tuned; the other six subjects were not touched.
- Two years of coexistence is a hard threshold; young projects adopt nothing. A relative threshold
  (share of the project's life) is the obvious next calibration, to be done on held-out subjects.
- "Unknown" is not the same as wrong. Several unknown adoptions are rules the team arguably should
  have (kedro: `io -> framework.hooks`); the benchmark cannot credit them.
- The learner cannot propose a rule the code currently breaks. Standing debt is invisible to it by
  design; that is what the hard rules and the repair loop are for.
- Rules about third-party packages (faststream: "only kafka imports aiokafka") are out of reach of
  an internal import graph and count as misses.
